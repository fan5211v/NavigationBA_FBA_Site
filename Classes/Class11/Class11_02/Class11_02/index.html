    Class 11.2 - 使用 API 获取数据¶

    1. API 基本介绍¶

    (1) API 的定义¶

    API 是应用程序接口（Application Program Interface）的缩写，是计算机和计算机程序之间建立"连接"的一套标准规则或程序：

    • 直白理解，API 就是使用程序来获取别的公司或组织的数据的，比方说用 R 代码、Python 代码等来获取数据，而不是直接下载 CSV 文件或 Excel 文件

    • 比方说 Twitter API，就是 Twitter 公司提供的，允许我们通过 Python 或 R 程序来将 Twitter 帖子下载到我们的计算机上进行分析

    • 事实上，Twitter 的 API 和 Twitter 的 APP 一样，都是从 Twitter 数据库调用数据：

      • 一篇帖子，如果被 Twitter APP 调用，这篇帖子就会出现在用户的手机上
      • 同一篇帖子，如果被 Twitter API 调用，这篇帖子就会出现在分析师的计算机上

    • 通过 API 我们可以调用各种各样的数据，但是 API 最常用的数据格式其实是 JSON：

      • 因为 JSON 不拘泥于严格的表格形式，可以包含层次结构和嵌套结构，适合表示复杂的数据关系
      • 同时 JSON 本质还是文本文件，占用空间小，易于传输和解析
    {
  "id": 12345,
  "text": "今天去海边玩耍了",
  "user": {
    "id": 67890,
    "name": "张三"
  },
  "created_at": "2024-01-01T12:00:00Z",
  "comments": [
    {
      "id": 54321,
      "text": "海滩人多吗？",
      "user": {
        "id": 98765,
        "name": "李四"
      },
      "created_at": "2024-01-02T08:00:00Z"
    },
    {
      "id": 54322,
      "text": "我也想去！",
      "user": {
        "id": 87654,
        "name": "王五"
      },
      "created_at": "2024-01-02T09:00:00Z"
    }
  ]
}

    API 的运行逻辑是：

    • 当你向 API 发送一个请求时，API 会处理这个请求并返回一个响应
    • 如果请求数据成功，响应将告诉你请求成功，并返回你请求的数据
    • 如果请求失败，响应将告诉你请求失败，以及失败的原因，例如，权限不足、请求格式错误、服务器错误等

    我们可以把这个过程想象成在图书馆向图书管理员请求一本书：

    • 在图书馆，有时候，你无法直接去书架找书
    • 在这种情况下，你可以向图书管理员提交请求，管理员会帮你从书架上取书
    图书馆类比 API 对应
    你 数据用户
    图书管理员 API
    只有员工可进入的区域 你无法直接访问的内部系统或数据库
    索书请求 你的程序发送给 API 的消息
    管理员取回的书 API 提供的数据或服务

    (2) API 与网页抓取¶

    在网上获取数据，除了 API，还有另一种常见的方式：网页抓取（Web Scraping）：

    API 网页抓取
    做法 数据提供方专门提供一个接口，直接返回结构化的数据（通常是 JSON） 用程序下载一个本来是给人看的网页，再从网页中把需要的数据提取出来
    数据的稳定性 稳定，格式有文档说明 容易失效，网页一改版，代码就可能失效
    适用场景 数据提供方提供了 API 没有合适的 API 时
    • 我们本节只学习使用 API，网页抓取不在我们的范围内
    • 需要提醒的是，不论是 API 还是网页抓取，获取数据时都要遵守网站的服务条款和相关法律，我们在后面的伦理章节中还会讨论

    (3) API 的优势¶

    如今，许多数据提供者将 API 设置为向数据用户提供数据的首选方式，有以下几个优势：

    • 受控访问：API 允许数据提供者只提供部分数据或功能，而不是给用户完全访问所有数据，有助于保护敏感数据和系统完整性
    • 标准化：通过提供标准化的数据访问方式，降低成本，因为用户无需自己开发复杂的数据获取程序
    • 创新和生态系统增长：API 允许第三方开发者直接在获取到的数据上构建应用程序和服务，促进创新和生态系统的增长，例如 Uber 调用了 Google Maps API，这样 Uber 的开发就可以专注于构建自己的核心功能，而不是重新开发地图功能
    • 使用追踪和管理：API 可以方便监控谁在使用数据以及使用频率，可以基于使用量进行收费，或者限制访问以防止滥用

    (4) API 的工作流程¶

    尽管每个 API 在许多方面可能差异很大，但基本的工作流程通常遵循以下步骤：

    1. 阅读 API 文档：这个是数据提供方给的 API 说明书，告诉你这个 API 能获取到什么数据，应该怎么用
    2. 获取 API 密钥：这个相当于账户密码，只有使用账户密码登录后才能获取数据提供方给的数据
    3. 发起 API 请求：通过代码告诉 API，我们想要什么样的数据
    4. 解析 JSON 响应：我们上面也提到了，API 通常返回的是 JSON 格式的数据
    5. 转化为可分析的表格：也就是我们上一章把 JSON 文件转化为表格的过程

    2. 在 R 中使用 API 获取数据¶

    本节我们以一个模拟的音乐数据库的 API（Music to Scrape）为例，来演示如何使用 API 获取数据并进行分析：

    • 这个模拟的音乐数据库包含了各种音乐相关的数据，例如歌曲、艺术家、专辑等，我们将通过 API 来获取这些数据
    • 这个 API 是一个教学目的的模拟 API，数据并不是真实的，只作演示，并且不需要密钥就可以访问

    API 通常返回结构化传输数据，而不是可直接分析的表格。收到 API 响应后，我们需要：

    1. 收到 API 响应并将其解析为 JSON 文本
    2. 将 JSON 文本解析为 R 列表
    3. 将 R 列表矩形化为 R 表格
    4. 清洗为整洁表格
    5. 存储为数据库表

    事实上，在这 5 个步骤中：

    • 2-5 其实都是我们上一章讲解 JSON 文件时已经介绍过的内容了
    • 本节的新内容主要是第 1 步：如何发起 API 请求并获取响应，以及API 响应的结构和内容是什么样的

    (1) 阅读 API 文档，构建请求¶

    使用 API 的第一步是阅读文档，Music to Scrape 的文档告诉我们：

    • 基础网址（Base URL）：https://api.music-to-scrape.org，它标识了这个 API
    • 端点（Endpoint）：基础网址后面的路径，标识了我们想要的数据类型，比如 /charts/top-tracks 是热门曲目榜单，/charts/top-artists 是热门艺术家榜单

    • 参数（Parameters）：用来描述我们想要什么样的数据，比如 /charts/top-tracks 有两个参数：

      • unixtimestamp：榜单统计的起始时间（Unix 时间戳，也就是从 1970-01-01 开始的秒数，回忆 2.4 节），统计的是从这个时间到现在的播放情况；如果不写，就是最近 7 天
      • limit：返回榜单的前几名，默认是 5

    一个完整的请求，其实就是一个网址：基础网址 + 端点 + ? + 参数，比如：

    https://api.music-to-scrape.org/charts/top-tracks?unixtimestamp=1777593600&limit=5

    在 R 中，我们使用 httr2 包来构建和发送请求（这个包是 httr 包的升级版，你在其他的资料中，可能会看到 httr 包的 GET() 函数，用法很类似）：

    library(tidyverse)
library(httr2)

# 定义 API 的基础 URL
api_url <- "https://api.music-to-scrape.org"

# 构建请求
req <-
    request(api_url) |>
    # 添加端点：路径的各部分用逗号隔开
    req_url_path_append("charts", "top-tracks") |>
    # 添加参数：统计的起始时间是 2026-05-01，返回前 5 名
    req_url_query(
        unixtimestamp = as.integer(as.POSIXct("2026-05-01", tz = "UTC")),
        limit = 5
    )

req

    <httr2_request>
GET https://api.music-to-scrape.org/charts/top-tracks?unixtimestamp=1777593600&limit=5
Body: empty
    • request() 指定基础网址，req_url_path_append() 添加端点，req_url_query() 添加参数，它们的作用都只是描述我们想要发送的请求
    • 注意，构建请求不等于发送请求：运行完上面的代码，我们还没有向 API 发送任何东西，只是得到了一个"请求对象"，打印出来的是它即将访问的完整网址

    这里有一个需要特别小心的地方：API 通常不会对写错的参数名报错，而是悄悄地忽略它们

    • 比如，如果我们把参数写成 week = 42, year = 2023（这些参数并不存在），API 不会报错，而是返回默认的"最近 7 天"的榜单，我们可能完全察觉不到
    • 所以我们一定要对照文档，并且检查返回的数据是不是我们想要的（比如检查返回的时间范围）

    (2) 发送请求，检查响应¶

    使用 req_perform() 函数来发送请求，得到的就是 API 的响应：

    resp <- req_perform(req)

resp

    <httr2_response>
GET https://api.music-to-scrape.org/charts/top-tracks?unixtimestamp=1777593600&limit=5
Status: 200 OK
Content-Type: application/json
Body: In memory (368 bytes)

    响应中包含了几个重要的信息：

    • 如果请求成功，响应会有成功的状态码（主要是 200），以及我们请求的数据
    • 如果请求失败，响应会有错误的状态码，以及错误信息，状态码的大致含义是：
    状态码 含义 例子
    2xx 请求成功 200 OK
    4xx 请求有问题（我们这边的原因） 404 Not Found（端点写错了）、401/403（没有权限）
    5xx 服务器有问题（对方的原因） 500 Internal Server Error
    • 我们可以用 resp_status() 函数查看状态码，用 resp_content_type() 函数查看返回的数据格式：
    resp_status(resp)
resp_content_type(resp)

    [1] 200
[1] "application/json"
    • 返回 200 和 "application/json"，表示请求成功，并且我们收到了熟悉的 JSON 格式
    • 如果请求失败（比如我们把端点写成了不存在的 /charts/nothing），httr2 默认会直接报错，提示 HTTP 404 Not Found，这样我们就不会误把错误的响应当成数据去分析

    (3) 解析响应为 R 列表¶

    使用 resp_body_json() 函数，可以一步完成"取出响应中的 JSON 文本，并把它解析成 R 列表"：

    top_tracks_list <- resp_body_json(resp)

typeof(top_tracks_list)
names(top_tracks_list)

    [1] "list"
[1] "unix_start" "unix_end"   "chart"
    • 返回的是一个列表（回忆上一章），顶层有三个键：unix_start（统计的起始时间）、unix_end（统计的结束时间，也就是我们发出请求的时间）和 chart（榜单本身）
    • 我们可以用 str() 查看列表的结构，并且指定只显示前两层：
    str(top_tracks_list, max.level = 2)

    List of 3
 $ unix_start: int 1777593600
 $ unix_end  : int 1792384318
 $ chart     :List of 5
  ..$ :List of 3
  ..$ :List of 3
  ..$ :List of 3
  ..$ :List of 3
  ..$ :List of 3

    • 结果显示：

      • chart 键对应的值是一个包含 5 个元素的列表
      • 每个元素又是一个包含 3 个键值对的列表，分别是 name、artist 和 plays

    • 因此我们可以尝试查看 chart 键对应的第一个元素：

    top_tracks_list$chart[[1]]

    $name
[1] "Right To Work"

$artist
[1] "Chelsea"

$plays
[1] 149

    事实上，我们可以看到，仅仅看热门歌曲，数据结构就已经很清晰了：

    • 每个歌曲都是一个列表
    • 并且包含共同的键：name、artist、plays
    • 因此，把这些歌曲放在一个表格中，每行对应一首歌，每列对应一个属性，就可以很方便地进行分析了

    (4) 矩形化为表格¶

    因此，我们将 chart 包装进 tibble，并直接用 unnest_wider() 展开（回忆 10.3 节）：

    top_tracks_tbl <- tibble(record = top_tracks_list$chart)

top_tracks_raw <-
    top_tracks_tbl |>
    unnest_wider(record)

top_tracks_raw

    | name <chr>               | artist <chr>          | plays <int> |
|--------------------------|-----------------------|-------------|
| Right To Work            | Chelsea               | 149         |
| In My Arms               | Snow Patrol           | 148         |
| Salzanitos               | Juan Carlos Baglietto | 147         |
| Famous Girl              | Chris Brown           | 143         |
| Les chasseurs d'esclaves | Gabriel Yared         | 143         |

    到此，我们就成功地将 API 返回的 JSON 数据转化为了一个整洁的表格了，接下来我们就可以直接进行数据分析了，例如：

    top_tracks_raw |>
    count(artist, sort = TRUE)

    | artist <chr>          | n <int> |
|-----------------------|---------|
| Chelsea               | 1       |
| Chris Brown           | 1       |
| Gabriel Yared         | 1       |
| Juan Carlos Baglietto | 1       |
| Snow Patrol           | 1       |

    top_tracks_raw |>
    slice_max(order_by = plays)

    | name <chr>    | artist <chr> | plays <int> |
|---------------|--------------|-------------|
| Right To Work | Chelsea      | 149         |

    top_tracks_raw |>
    summarise(sum_plays = sum(plays))

    | sum_plays <int> |
|-----------------|
| 730             |
    • 需要说明的是，这个 API 返回的是实时的数据，统计的时间范围是从我们指定的起始时间，到我们发出请求的这一刻，所以你在不同的时间运行同样的代码，得到的结果可能会和这里展示的不一样
    • 这也提醒我们：如果分析需要可复现，我们应该把从 API 获取到的数据，保存下来（比如用 write_csv() 保存成文件），而不是每次都重新请求

    4. 把请求封装成函数¶

    到目前为止，每获取一次榜单，我们都要把"构建请求 → 发送请求 → 解析 → 矩形化"的代码重新写一遍，如果我们想获取很多个不同起始时间的榜单，这样做就太繁琐了。这时，我们可以把这一整套步骤，封装成一个函数。

    (1) R 中函数的定义¶

    回忆 2.3 节，函数是一个"加工厂"，我们前面一直在使用别人写好的函数，现在我们来学习定义自己的函数：

    定义函数的格式是 函数名 <- function(参数1, 参数2 = 默认值) { 函数体 }，我们来看一个最简单的例子：

    add_n <- function(x, n = 1) {
    x + n
}

add_n(5)
add_n(5, n = 10)

    [1] 6
[1] 15
    • 参数是函数的"输入"，其中可以给参数设定默认值（比如 limit = 5），这样调用函数时，如果不写这个参数，就会使用默认值
    • 函数体是用花括号 { } 包起来的一系列代码，函数运行时，会按顺序执行
    • 函数体中最后一行代码的结果，就是函数返回的值

    (2) 封装 API 请求¶

    我们来决定一下，哪些东西应该写在函数里面：

    • 固定不变的：基础网址、端点
    • 每次可能不同的（作为函数的参数）：起始日期 start_date，返回的名次数量 limit
    get_top_tracks <- function(start_date, limit = 5) {
    resp <-
        request(api_url) |>
        req_url_path_append("charts", "top-tracks") |>
        req_url_query(
            unixtimestamp = as.integer(as.POSIXct(start_date, tz = "UTC")),
            limit = limit
        ) |>
        req_perform()

    tibble(record = resp_body_json(resp)$chart) |>
        unnest_wider(record) |>
        # 增加一列，记录这个榜单的起始日期，这样把多个榜单合并之后，我们还能知道每一行来自哪个榜单
        mutate(start_date = start_date)
}

    现在，获取一个榜单就只需要调用这个函数了：

    get_top_tracks("2026-05-01")

    • 如果没有提供没有默认值的参数（这里的 start_date），函数就会报错：argument "start_date" is missing, with no default

    5. 重复执行：批量获取多个榜单¶

    有了函数，我们就可以批量地获取多个起始时间的榜单了：

    start_dates <- c("2026-01-01", "2026-04-01", "2026-07-01")

    (1) 使用 for 循环¶

    for 循环的作用是：把一件事重复做很多次，每次处理一个不同的对象：

    # 先创建一个空列表，用来存放每次获取的结果
results <- list()

for (i in seq_along(start_dates)) {
    results[[i]] <- get_top_tracks(start_dates[i], limit = 3)
}

# 把列表中的每个表格上下拼接在一起
all_tracks <- list_rbind(results)

all_tracks

|-----------------------------------|-----------------------|-------------|------------------|
| Devon                             | Gabriel Yared         | 238         | 2026-01-01       |
| Orbit                             | Megadrums             | 236         | 2026-01-01       |
| Locust Reign (Live in California) | Converge              | 236         | 2026-01-01       |
| I Will (Patitu)                   | UKW                   | 177         | 2026-04-01       |

| Salzanitos                        | Juan Carlos Baglietto | 100         | 2026-07-01       |
| Clothes Of Sand                   | Solas                 | 100         | 2026-07-01       |
    • seq_along(start_dates) 生成 1, 2, 3，也就是每个日期的位置，for 循环每次取一个位置 i，把 start_dates[i] 交给函数，结果存放到列表 results 的第 i 个位置
    • 最后用 list_rbind()（purrr 包中的函数，tidyverse 中已经包含）把列表中的所有表格拼成一个大表格
    • 这样，我们用 3 行代码，就获取了 3 个榜单

    (2) 使用 map() 函数¶

    for 循环写起来比较啰嗦，purrr 包提供了 map() 函数，用一行代码就可以实现同样的效果：

    all_tracks_map <-
    map(start_dates, get_top_tracks, limit = 3) |>
    list_rbind()
    • map(x, f, ...) 的意思是：把 x 中的每个元素，依次交给函数 f 的第一个参数，并且把后面的参数（这里的 limit = 3）固定不变地传给函数，最后把所有的结果放在一个列表里
    • 因此，map(start_dates, get_top_tracks, limit = 3) 就相当于上面的 for 循环，得到的结果和 for 循环的结果是完全一样的

    (3) 同时变化两个输入¶

    如果我们想让起始日期和名次数量同时变化，可以先用 expand_grid() 生成所有的组合，再用 map2() 函数，把两个输入，成对地交给函数：

    request_grid <- expand_grid(
    start_date = start_dates,
    limit = c(2, 3)
)

|------------------|-------------|
| 2026-01-01       | 2           |
| 2026-01-01       | 3           |
| 2026-04-01       | 2           |
| 2026-04-01       | 3           |
| 2026-07-01       | 2           |

    map2(request_grid$start_date, request_grid$limit, get_top_tracks) |>

    • expand_grid() 生成了 3 × 2 = 6 个"起始日期 × 名次数量"的组合，也就是 6 个请求，map2() 把每一行的 start_date 和 limit 成对地交给 get_top_tracks()
    • 6 个请求返回的行数是 2 + 3 + 2 + 3 + 2 + 3 = 15 行
    • 这样的做法可以很轻松地扩展：如果有 50 个起始日期，只需要把 start_dates 改成 50 个，代码的逻辑一点都不用改，这就是"可复现的数据获取流程"

    6. 使用 API 的注意事项¶

    最后，在实际使用 API 时，还有一些需要注意的事项：

    • 请求频率限制：很多 API 会限制单位时间内的请求次数，如果请求太快、太多，可能会被暂时封禁，批量请求时，要注意放慢速度，比如在请求之间加上等待（Sys.sleep(1)，或者在请求中使用 req_throttle() 限制请求的速率）
    • API 密钥：很多 API 需要密钥才能访问，密钥相当于账户密码，不要直接写在代码里，更不能把它上传到公开的地方，比较安全的做法是把密钥保存在环境变量中，然后用 Sys.getenv() 读取
    • 服务条款与伦理：使用 API 之前，要阅读数据提供方的服务条款，了解数据能不能用于商业用途、有没有使用限制，另外，如果数据涉及个人隐私，还要遵守相关的法律和伦理规范（我们在伦理章节中会进一步讨论）
    • 数据的变化：API 的数据和规则都可能变化，今天能运行的代码，过一段时间可能就需要调整，所以，把获取到的数据保存下来，是一个好习惯
    • 检查返回的结果：不要想当然地认为请求成功了，数据就是我们想要的，要检查状态码，也要检查返回的内容（比如这里的统计时间范围）是否符合预期

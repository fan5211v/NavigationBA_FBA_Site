    Class 10 知识点总结¶

    Class 10 讲的是数据存储，主要介绍各种数据存储的形式：

    • 四种存储方式的对比概览
    • JSON 的结构和矩形化
    • 数据库的概念以及查询

    1. 四种存储方式¶

    电子表格（Excel / Google Sheets）：

    • 数据文件类型：二进制文件

    • 适合场景：

      • 轻量数据的快速探索
      • 与非技术人员协作

    • 主要局限：

      • 难以处理大规模数据
      • 不会记录操作历史
      • 团队协作困难，并且不支持版本控制

    平面文件（CSV / TSV）：

    • 数据文件类型：文本文件

    • 适合场景：

      • 数据分享，或者跨平台跨工具使用，因为文本的可移植性好
      • 可复现的脚本分析

    • 主要局限：

      • 一个文件就是一张表，要么不同信息要拆成多个文件，要么一张表里要重复存储层次结构
      • 不存列类型，所有数据都是文本，需要读入时自己指定列的类型

    JSON（全称 JavaScript Object Notation）：

    • 数据文件类型：文本文件

    • 适合场景：

      • 数据结构不固定，可能是嵌套的对象或数组
      • 通常 API 返回的数据就是 JSON 格式

    • 主要局限：

      • 结构灵活不固定，难以直接分析
      • 分析前要先矩形化

    数据库（DuckDB / SQL）

    • 数据文件类型：二进制文件

    • 适合场景：

      • 大规模数据存储和分析
      • 多人共享和协作
      • 多表关联查询

    • 主要局限：

      • 需要连接配置
      • 需要掌握查询语言（如 SQL）

    2. JSON¶

    (1) JSON 的结构¶

    JSON 文件的核心结构类似于 Python 中的字典，是由键值对构成的嵌套组合：

    • 键就是这个数据的名称

    • 值就是这个数据所存储的内容，值可以包括：

      • 单个值：字符串、数值、布尔值、空值等
      • 数组：一列值，由 [] 包裹
      • 字典：由 {} 包裹，里面是键值对

        "gender": "male",

    JSON 在读取进来之后，它会变成一个 R 中的 list

    • R 的 list 和 JSON 的嵌套结构一模一样，只不过嵌套表示方式不同：

      • JSON 的字典 {} 结构会变成 R 的 list 中的子 list，用 $ 来表示，用来 $ 访问
      • JSON 的数组 [] 结构会变成 R 的 list 中的数组，用 数字. 来表示，用 [[ ]] 访问

    • 例如：

      • 要访问第一个学生的姓名，可以用 students_nested[[1]]$name
      • 要访问第一个学生的第一个爱好，可以用 students_nested[[1]]$hobbies[[1]]
      • 要访问第二个学生的第一个奖项的名称，可以用 students_nested[[2]]$awards[[1]]$name
    students_nested[[1]]$name
students_nested[[1]]$hobbies[[1]]
students_nested[[2]]$awards[[1]]$name

    (3) JSON 矩形化¶

    矩形化（Rectangling）：把 JSON 的嵌套的结构变成行和列整齐的表，大家记住我发明的口诀：

    • 遇到 JSON 字典，也就是 R 的子 list --> 变宽：unnest_wider(col)：把字典里的每个键展开成新的列，列变多，行数不变
    • 遇到 JSON 数组，也就是 R 的数组 --> 变长：unnest_longer(col)：把数组里的每个元素展开成新的行，行变多，列数不变

    3. 数据库¶

    (1) 为什么需要数据库¶

    当数据量很大的时候，我们上面介绍到的数据格式会有一些局限性：

    • Excel 或 文本文件在读取的时候会很慢，甚至可能无法一次性全部读入内存
    • 文件的存储和管理也比较分散，不利于多人协作和复杂查询，难以保证数据的一致性

    因此，数据库数据库专门为这些需求设计：

    • 数据库通过查询来访问和操作数据，而不需要一次性把所有数据读入内存
    • 数据库支持多人同时访问和操作数据
    • 数据库可以处理复杂的查询和多表关联
    • 缺点是部署复杂，需要配置数据库环境，并且需要会写查询语句

    我们本门课学的数据库是 DuckDB，它是一种轻量级的数据库，它的特点是：

    • 数据库就是一个文件，例如我们课上用的 auctions.duckdb
    • 一个数据库文件中，可以包含多张表，例如 auctions.duckdb 数据库里有 auctions 表和 bids 表
    • 多张表之间可以通过我们之前学过的表连接来关联在一起

    (2) 在 R 里查询数据库¶

    在 R 里查询数据库时，我们通常先建立连接：

    library(DBI)
library(duckdb)

con <- dbConnect(duckdb(), "auctions.duckdb", read_only = TRUE)
    • 这里 dbConnect() 的作用是连接数据库，得到的连接对象是 con
    • 我们这里还只是创建了一个数据库连接，还没有任何的数据查询

    接下来，我们就可以进行数据查询：

    • 我们来看一个典型的数据查询代码例子：
    bid_summary <- tbl(con, "bids") |>
    group_by(item_id) |>
    summarise(
        n = n(), 
        top = max(bid_amount)
    ) |>
    collect()

    • 在这段代码中：

      • 我们用 tbl(con, "bids") 表示要查询数据库里的 bids 表
      • 之后的后面的 group_by 和 summarise 都表示我们要在数据库里进行的操作
      • 最后用 collect() 把查询结果取回 R

    • 要注意的是：

      • 在调用 collect() 之前，数据还没有被读取进 R，只是一个查询对象
      • 只有调用 collect() 后，查询结果才会被取回 R，变成普通的 tibble
      • 并且对数据的查询使用的函数，其实和我们在之前学的数据处理的函数是一样的，例如 filter、group_by、summarise 等，区别在于它们是在数据库里执行的，而不是在 R 的 tibble 上执行的

    (3) 展示查询对应的 SQL 代码¶

    我们可以对一个查询对象使用 show_query() 来查看它对应的 SQL 代码：

    tbl(con, "bids") |>
    group_by(item_id) |>
    summarise(
        n = n(), 
        top = max(bid_amount)
    ) |>
    show_query()

    <SQL>
SELECT item_id, COUNT(*) AS n, MAX(bid_amount) AS top
FROM bids
GROUP BY item_id

    这里我们简单了解即可，因为 SQL 大家到大二才会去学，我们了解基本概念就好：

    • 调用 show_query() 可以查看对应的 SQL 代码
    • 它只会打印 SQL 代码，不会取回任何数据

    (4) 断开数据库连接¶

    在用完数据库之后，我们需要断开连接，释放资源：

    dbDisconnect(con, shutdown = TRUE)
